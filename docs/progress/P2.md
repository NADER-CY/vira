## 2. What was built

### Backend (Go modular monolith, existing module boundaries)
| Module | Scope |
|---|---|
| `identity` | Iranian mobile numbers (09…, +989…, Persian digits), 6-digit OTP via the SMS simulator, account-type intent, explicit versioned consents (terms, privacy, age), devices, sessions, rotating refresh tokens with replay detection (reuse revokes the session), logout, sign out other devices, account status (active / restricted / suspended / deletion_pending / deleted) with history, 30-day deletion request cancelled by signing in, recovery-request foundation, admin user management |
| `social` | Profiles (avatar, name, handle, bio, link, privacy), follow / unfollow, follow requests for private accounts, remove follower, blocks (bidirectional invisibility), posts (images, caption, audience) create / edit / delete with ETag/If-Match, home and following feeds with cursor pagination, likes, comments (own delete, post-owner delete), user search |
| `media` | Image upload (type sniffing, size and pixel limits, re-encode strips EXIF), object storage (MinIO in dev) |
| `moderation` | Reports on posts, comments and accounts (rate limited, duplicate-safe), report queue, resolutions (dismiss, remove content, restrict, suspend) closing co-reports, summaries |
| platform | Valkey rate limiter (per phone, per device, per IP as a high anomaly threshold — CGNAT, audit F-24), object store client, SMS provider interface + simulator, config |

Every write is audited (`TestEveryWriteIsAudited`); phone numbers are stored AES-256-GCM encrypted with a blind index
and only ever returned masked (`09*****4567`). All regulated flags remain locked off (DB CHECK from Phase 1).

### Migrations (reversible; up/down tested in the `migrations` job)
- `0004_identity` — users, phone_identities, otp_challenges, devices, sessions, refresh_tokens, status_history, recovery_requests, consents
- `0005_social_media` — media.assets, profiles, follows, follow_requests, blocks, posts, post_media, likes, comments
- `0006_moderation_admin` — moderation.reports, Phase 2 admin permissions (users.read/write, reports.read/write)

## 5. Security-related UI issues (reported, not redesigned)

- `otp`: implicit terms text («با ورود … می‌پذیرید») → consents are three separate, unticked, versioned boxes
  (UC-5). The account-type choice keeps the reference's default (social user); it records an intent only and grants
  nothing — seller status needs the Phase 4 verification.
- `_205`: claims "SSL v3", active 2FA, authenticator and backup codes — none exist in P2; the texts state what is true.
- `_213`: «۱۰۰٪ ناشناس» and «رمزنگاری سرتاسری» overstate; reports are confidential to staff, wording adjusted.
- `vira_users_management`: unmasked phones/e-mails → masked phones only; no e-mail collected. Bulk checkboxes and
  CSV export have no P2 backend and are omitted (no fake controls); "Shahkar rate" tile shown inactive (P4).
- `vira_comments_reports_dark`: header "instant settlement" button not reproduced (doc 19, V-06).

## 6. Known issues and limits

- **SMS is the simulator only.** No real provider is integrated; live SMS is not claimed (D-12 open).
- Legal texts for consents are placeholders (`p2-draft-1`) until counsel approves them (D-13).
- Notifications inbox (beyond follow requests in Activity) and saved posts are not in the P2 instruction and are not built.
- Goldens use synthetic data without network images, so post images render as placeholders in the sheets.
- Admin user list: role filter is inactive until sellers exist (P4); pager is previous/next (cursor-based).
- `main` branch protection is still not enforced: the ruleset `.github/rulesets/main-protection.json` must be imported
  by the owner (Settings → Rules → Rulesets → Import). Required checks: backend-test, migrations, dev-stack-smoke,
  contracts, web-build-test, mobile-build-test, secret-scan, go-vulnerabilities; PR required; no force-push or deletion.
- No production deployment; all regulated flags locked off.
