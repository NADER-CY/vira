# VIRA Phase 0 — Independent Architecture Audit Findings

**Auditor stance:** independent reviewer; did not author docs 02–13.
**Scope reviewed:** brief (`attachment.txt`), Master Requirements v0.1, UI manifest (checked with Python), docs `00_README`, `02`–`13`, `02a` CSV.
**Checked by computation:** the inventory counts (277/106/53/382/231+46/`_42`=`_17`, 166 Latin-only screens: all correct), the status and domain totals in the CSV (correct), the WCAG contrast ratios in doc 09 (correct), the egress, storage and transcoding arithmetic in doc 10 (correct), and the ledger worked example in doc 06 §6.2. Every entry balances, and the closing trial balance ties out: BANK 361,000 = SELLER_AVAILABLE:B 267,000 + TAX 9,000 + (revenue 90,000 − PSP fee 5,000). **The arithmetic is right. The problem is what the example leaves out (see F-05, F-06).**

Severity counts: **CRITICAL 2 · HIGH 9 · MEDIUM 14 · LOW 5** (30 findings).

| F-07 | HIGH | Financial / Iran-specific PSP integration | 07 §4.3, rules 2–6; 04 TB6; 08 T04 | **The PSP protocol assumptions are too generic and in places wrong.** (1) The callback is described as "signed" and protected by a "PSP IP allowlist". Common Iranian IPG callbacks are **browser-mediated form POSTs/redirects**: unsigned, and arriving from the buyer's IP, so an IP allowlist would block legitimate callbacks. (2) Some PSP protocols need a separate **settle** call after verify (e.g. Behpardakht/Mellat verify + settle); without it the payment is reversed. (3) PSPs return a distinct "already verified" code on a duplicate verify. The flow's `verify failed → attempt failed` branch would mark a paid attempt as failed. (4) If verify succeeds but T2 then fails (DB error or exhausted serialization retries), no inquiry is scheduled. That path enqueues inquiry only on "timeout / PSP error", so the money is captured but the order stays unpaid until next-day reconciliation. (5) Amount units differ by PSP (Rial vs Toman), a ×10 risk. (6) A PSP order ID is often required to be unique and numeric per attempt. | 04 TB6: "signed callbacks verified **and** re-queried". 08 T04: "PSP IP allowlist". 07 rule 2: "verify is idempotent per PSP token". | Treat the callback as an untrusted hint. Bind it to the attempt with a server-generated nonce in the callback URL. Model a per-PSP adapter state machine with `verify → settle`, with "already verified/settled" codes mapped to success after an inquiry. Persist the verify outcome (`attempt=verified`) in its own committed step **before** T2, and always enqueue a reconciler job. Give the adapter an explicit amount unit and a numeric `order_id` sequence per attempt. Get the exact PSP behaviour from the signed contract and the sandbox, and record it in an ADR. |
